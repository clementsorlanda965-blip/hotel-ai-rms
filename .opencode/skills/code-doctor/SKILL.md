## 强制规则

所有文字输出必须是中文。分阶段执行，每个阶段有明确检查点。

## 管线总览

```
用户报bug/请求检查代码
  │
  ▼
Phase 1 ▸ 诊断（定位根因）
  加载 systematic-debugging ← 系统化排查
  │
  ▼
Phase 2 ▸ 测试先行
  加载 test-driven-development ← 写失败测试，确认能捕获 bug
  │
  ▼
Phase 3 ▸ 修复
  修改代码 → 测试变绿
  │
  ▼
Phase 4 ▸ 重构
  加载 code-refactor ← 清理冗余、改善结构
  │
  ▼
Phase 5 ▸ 审查
  加载 requesting-code-review ← 自我审查
  加载 verification-before-completion ← 最终验证
  │
  ▼
输出：修复摘要 + 测试结果
```

## 阶段一：诊断

**目标：** 找到根因，不猜测、不盲目修复。

1. 先运行项目测试/构建命令，收集所有失败信息
2. 加载 `systematic-debugging` skill，系统化定位根因
3. 定位到根因后，确认理解：**是什么导致了这个问题？**
4. 向用户报告根因和修复方向，等待确认再进入下一阶段

**检查点：** 是否真正找到了根因？是否能复现？是否确认了修复方案？

## 阶段二：测试先行

**目标：** 先写一个能复现 bug 的测试，修复前确保测试是红的（失败）

1. 加载 `test-driven-development` skill
2. 找到或创建对应的测试文件
3. 写一个能复现 bug 的测试用例（红）
4. 运行测试确认它是红的

**检查点：** 测试是否准确反映了 bug？是否是红的？

## 阶段三：修复

**目标：** 修改代码让测试变绿

1. 根据阶段一的根因分析，修复代码
2. 运行所有测试，确认通过（绿）
3. 不要过度修复，只改必要的地方

**检查点：** 所有测试通过？没有引入新的失败？

## 阶段四：重构

**目标：** 优化代码质量，不改行为

1. 加载 `code-refactor` skill
2. 检查修复区域的代码质量：未用变量、死代码、重复块、嵌套深度、命名
3. 分步重构，每改一步运行一次测试确认不破坏功能
4. 回滚任何导致测试失败的修改

**检查点：** 测试是否仍然全绿？重构是否只改了结构没改行为？

## 阶段五：审查 + 验证

**目标：** 最终把关，确保交付质量

1. 加载 `requesting-code-review` skill，做一次自我审查
2. 审查视角：是否有遗漏的边界情况？修改是否完整？
3. 加载 `verification-before-completion` skill
4. 最终运行全量测试套件
5. 如有 lint/typecheck 命令，一并运行

**检查点：** 所有检查通过？

## 交付

输出修复摘要，格式如下：

```
## 修复摘要

**问题：** <一句话描述 bug>
**根因：** <根因分析>
**修改文件：** <文件路径:行号>
**修复方案：** <做了什么>
**测试结果：** ✅ 全部通过（X 个测试）
**审查结论：** <有无风险>
```

## 边界情况

| 场景 | 处理方式 |
|------|---------|
| 项目没有测试 | 阶段二跳过，告知用户无测试框架/测试文件 |
| 无法复现 | 阶段一报告"无法稳定复现"，给出监控/增加日志的建议 |
| 根因不明确 | 增加诊断日志，缩小范围，汇报给用户后再决定方向 |
| 测试失败不是因为用户报告的 bug | 仍然先修复 bug，再把额外失败报告给用户 |
| 修复风险高 | 阶段三前与用户确认，或提供多个方案选择 |
